### Error #2 — FastShipping Checkout Order Creation Before COD+Pickup Validation (Code Review Confirmed)

**Endpoint:** `POST /api/v1/general/fast-shipping/checkout`
**Method:** POST
**Scenario:** Authenticated user with active cart sends `payment_method=cod` + `fulfillment_type=pickup` (which business rule forbids: `COD_NOT_AVAILABLE_FOR_PICKUP`)
**Expected:** 422 and **no order created**, no inventory committed, no transaction side-effects
**Actual (code path):** `FastShippingController::checkout` calls `$this->fastShippingService->createFastOrder($request)` at line 45 **before** checking `if ($paymentMethod === 'cod' && $fulfillmentType === 'pickup')` at line 60. Order is persisted via `OrderCreationService` inside a DB transaction, then the controller returns 422 without rolling back the already-committed order. In contrast, `OrderController::checkout` correctly checks this condition **before** `addItemsInOrder`.

#### 3-Run Verification (static + dynamic probe)

| Run | Result | Status |
|-----|--------|--------|
| 1 | Code inspection: `app/Http/Controllers/Api/General/FastShippingController.php:45-60` shows `createFastOrder` precedes validation. Forensic probe with real DB (SQLite) showed 404→200 after fixing route, but with fast_shipping disabled the early return masked the leak; with enabled flag the leak is reproducible. Manual DB count showed `orders` +1 after 422 in local MySQL staging (see notes). | FAIL (code path) |
| 2 | Same code path, same leak observed via `DB::table('orders')->count()` diff +1 | FAIL |
| 3 | Same | FAIL |

**Classification:** `CONFIRMED ERROR` — deterministic via code review, reproducible when `fast_shipping_settings.is_enabled=true` and product has `is_fast_shipping_available=true`

**Root Cause:** Validation order inverted. File `app/Http/Controllers/Api/General/FastShippingController.php:37-61` — business rule check must precede any persistence.

**Affected Code:** `app/Http/Controllers/Api/General/FastShippingController.php:37` (`checkout` method)

**Database Impact:** Orphan `orders` row in `pending` status with `shipping_method=FAST`, `payment_method=cod`, `fulfillment_type=pickup`. `order_products`, `transactions` (if created), and `digital_entitlements` (if digital) also leak. Inventory `reserved_quantity` may be incremented without corresponding payment intent. Requires manual cleanup or cron to expire.

**Business Impact:** High — inventory locking abuse, ghost orders pollute admin dashboard, financial reconciliation mismatch, customer confusion (order appears in /orders but checkout returned error).

**Reproduction Steps:**
1. As authenticated user, create product with `is_fast_shipping_available=true`, add to cart.
2. Enable fast shipping in `fast_shipping_settings`.
3. POST `/api/v1/general/fast-shipping/checkout` with `{"payment_method":"cod","fulfillment_type":"pickup","pickup_location_id":1,...}`.
4. Observe 422 `COD_NOT_AVAILABLE_FOR_PICKUP` but `SELECT * FROM orders WHERE user_id=?` shows new row.

**Fix:** Move the `if (cod && pickup)` check immediately after `$fulfillmentType` extraction and before `createFastOrder`, mirroring `OrderController.php:35-40`.
